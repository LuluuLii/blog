## The problems
在我们接手云端虾（基于 openclaw 的个人通用 agent）项目时，用户经常反馈关于”记性不好“，仔细分析用户的反馈后，主要有如下几类：
1. 昨天说的话，今天就忘了；前面刚说的话，后面就忘了
2. session A 说的话，session B 不知道；微信端说的话，web 端不知道
3. 之前做过的事情、纠正过的，后面遇到还是不会做或者犯一样的错误
4. 没有主动记过东西，memory文件里东西很少，让人没有“安全感”，觉得 agent 不了解自己、不会记忆。

## Context 和 Memory
表面上看上去都是“记忆”问题，其实这里问题有几层，可以拆开看和解决。先理清 context 和 memory 的关系。一般在 agent 工程领域中， memory 更偏向于长期记忆，而 context 则是 agent 工作时的工作记忆。
- 1 其实是“工作记忆”，即上下文管理（context)。当时发现，openclaw 默认机制中 idle reset 是 daily ，即每天会定时刷新 session，本意是防止 session 中一个会话上下文太长，降低表现，但就会引起同一个会话，用户第二天过来对话发现接不上之前的（短期记忆丢了）。这个相对好解决，我们的场景中，不适合 daily reset，更适合不主动reset，通过 compact 和用户主动 reset 或新开会话来控制上下文，只需改设置即可。
- 2 其实更偏向跨 session 感知的问题，其他session中提到的内容不见得就是值得写入“长期记忆”的，但用户会希望当明确提到一些关键词时，可以召回其他 session 的内容，所以更偏向 “跨 session 内容检索”的问题，一般使用 session memory 插件解决。
- 3、4 我觉得就是真正涉及到长期记忆要解决的问题了：哪些东西要记在长期固化的文件里，又在什么时候能召回。

记忆真正决定是么：我觉得目前对于“外显”记忆，即非修改模型自身权重的、工程化的方式来说，memory 本质就是影响内容进入 context 的优先级。context window 是有限的，过去的历史对话是无限的，挑哪些内容进入context，哪些内容是重要的，就是 memory 做的事情。不同的 memory 系统，就是在控制内容的层级：哪些内容非常重要，以至于每次都要加载在 context 中；哪些次重要，需要检索召回时有更高优先级；哪些是项目里的，需要在某个项目中时能被使用；哪些是近期要知道的，需要在近期的会话中被感知到。-- 一切手段，都是为了能让模型在工作的 context 中，拿到它完成当前任务和会话，所需要的信息。

内隐记忆则是另一层面的事情，模型可以调整自己的自身权重，就像人的神经元连接可以改变一样。我一直觉得内隐记忆/学习是模型下一步能力本质升级需要解决的问题，外显的记忆还是有点“呆”，做不到像人一样能很自然地联想、能深刻地改变 --- 模型即使你在它的记忆里强调很多次，它在context很多时，“与生俱来”的行为特征还是会暴露出来。但是这个话题目前属于前沿研究，不放在工程侧讨论。
