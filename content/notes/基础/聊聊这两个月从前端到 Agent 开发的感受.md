### The background 
前几个月，突然部门通知，我们组原地转全栈开发。我们当时负责一个 agent 产品的前端，宣布这个产品的后端全部撤出，由我们之前的前端负责前后端所有的开发，两周交接期。当然说是两周交接期，但对面也有新任务了，对旧的项目交接清楚已尽到责任，于是我们就这样非常迅速地当天就开始进入所谓的全栈开发。现在已经度过了比较手忙脚乱的时期了，打算回顾下，也给一些面临转型的朋友参考。

先说下背景，我们组其实从半年前就开始陆续接触一些“全栈”业务，做过：产品答疑 agent（涉及数据收集、RAG）、网页生成效果评测（涉及沙箱、评测集构建）、图标检索（涉及向量数据库、多模态embedding）、coding agent (类似封装云端7\*24小时的 claude code)，对 agent 链路和后端常用的服务有一些基础的了解，再加上 claude code 的鼎力相助，上手业务不算太陡峭。我现在回想，对想转全栈开发的前端同学来说，上面我说的几个业务确实是不错的切入点：从和前端沾边的点切入（发挥自己的专业特色）、有实际落地场景、难度不大但走通链路也能熟悉不少全栈开发链路。

说回这两个月真正意义上的 agent 开发。我们业务简单来说就是 1. 提供运行在云端的个人通用 agent 助手，2. 提供 agent 构建平台。这类平台很多很多，大家可以想象，保护隐私我就不细展开了，说些我觉得对于想要进入 agent 开发这个领域，一些值得去了解的概念和对前端来说可能相对陌生的地方：
1. 基础
	1. 对于agent业务和后端这个领域来说，虚拟化技术都是比较重要的概念，所以放在第一位说：容器、镜像、k8s。
		1. 持久化：长任务需要持久化的概念、各种持久化手段的特点：比如Nas读写慢等
		2. 有状态服务和无状态服务
	2. unix、shell、bash
2. Agent 的一些概念：agent loop、RAG、LLM 等 这些我觉得是近来非常火热的，经常刷刷讨论和博客，大概能理解得差不多
3. 对于“通用后端”业务，也就是数据的增删改查了
	1. 几种数据库和存储选择
		1. 数据库事务、ACID四大特性、五种事务属性
	2. 和前端差异比较大的，容易踩坑的地方：
		1. 数据的并发、分布式问题
		2. 有状态服务 vs 无状态服务
	3. 服务端模型：
		1. controller-service-mapper
		2. 业务抽象层--dao层+dao实现层 涉及到两个不同数据库操作（mysql+bigData），使用DS可以快速切换数据源，并且还具备跨库事务操作
		3. 模块划分、层级结构、事务、数据链路、定时任务、多级缓存、服务注册与发现
	4. 失败和异常的处理
		1. 当前端的时候，真的没想到后端系统那么地脆弱，经常心里想后端怎么那么不靠谱，简简单单一个小接口还会报错，前端捕获和处理报错也相对简单。但后端系统真的还挺不稳定的，失败后还容易导致各种的不稳定性 还需要回滚状态等 这些细节的讨论
		2. 数据库读写失败、数据库大小超出限制
		3. 数据库并发量、外部依赖服务的吞吐量
		4. 瞬时状态错误
		5. 长任务的特殊关注：大文件还没传输完连接断了
		6. ！！内存泄漏问题
4. ！！安全问题 接口攻击
5. 你的前端知识可以相通的地方或者说也是对自己之前知识一个更深入的理解
	1. 网络通信 跨域问题 网关问题：比如公司内网请求外网、server to server 的机制、请求到底是打到哪个机器、router、dns
	2. 权限 鉴权
6. 其他一些通用技能：
	1. 建立排查问题的直觉和方法：打日志和排查日志（trace） — 后端机器是分布式的，日志要聚合来看
	2. 测试方法
7. 也可以给后端同学分享一点前端开发的经验吧，虽然可能并没有人想认真学习前端（？
	1. Ai操作浏览器以及看日志 
	2. 前端的自动化测试
	3. 组件思路 react MVVM模型
8. 如果你是产品/设计转型开发，或者只是想要自己做点demo、和研发更高效合作（比如验收完自己盖点简单的问题）
	1. 了解 git，和 claude code 协作git
	2. 熟悉 claude code
	3. 熟悉本地启动项目、代理和验证

虽然这些你跟 ai 说，它能理解、定位问题和寻找方案，但你不知道它可能也没想到，就会掉进坑里，只能靠自己积累和补充知识和视角了。

一个相对好实操的办法就是，在后端系统里叠 layer 的时候，调用或者增加服务的时候，都要问 ai 和自己，如果这一层失败了怎么办。以及有没有引入这一层的必要，系统复杂性还能不能降低。

当然，这种判断力没啥捷径，只能“试错”，在线上问题和安全的鞭打下，复盘、沉淀。

### The differences I experienced
传统前后端能力视角和能力发展模型的不同:
1. 前端天然在意可复用性 天然在意人机友好
2. 后端天然跟业务走得更近

### The mindset and the future work
如果你想转后端，我觉得不用焦虑。去年我也在想

首先可以心态上祛魅，我看了后端代码后感觉也是漏洞百出（当然这可能是因为我们是个小业务，不过我觉得公司业务代码都是堆砌为主吧

虽然祛魅，但我不认为后端开发是完全没有门槛的，也不认为专业的积累是靠 ai 能快速抹平掉的，只是时代给了大家一个重新选择、快速学习新领域和切换领域的机会，还是需要通过踏实学习和复盘去真正掌握和积累。下面我也列一些我觉得如果想从前端转到后端需要理解的概念和补的知识。

但我觉得现在一个很危险的趋势是，这种工作方式对人的消耗其实是很大的，容易滑入堕于思考的深渊。以前传统研发模式下，我们会写设计文档、开评审会、和后端对齐技术方案、和横向兄弟团队对齐组件库需求和复用度，虽然一轮轮对齐确实有很多低效和冗余在，但也是在不同视角的人进来挑战、交叉质疑和确认中，你自己也把思路想得很清楚，在手动实现时，也会因为不好的设计感到痛苦，这种痛苦会驱动你改善不良的设计。

现在全栈做业务后，变成真正的“只要解决业务需求就行” 变成“不用太在意组件”，ai进来包揽代码后，痛苦没有了，即使架构非常不合理，但 ai 就是能一层层通过各种手段给问题“解决了”。但是问题其实是被掩盖了，大量的垃圾开始狂野生长，直到你不想思考也不能思考，也不敢踏入杂草丛生的业务代码库里一步。

我觉得少了很多锤炼后，很担心人的判断力和一些基本功会下降。基本功是要一些纠结的方案反复和琐碎来锤炼出来的。我其实没那么害怕职业的更迭，我也在积极考虑换一些职业方向，但是我确实怕自己的思考能力和动手能力的下降。不管
