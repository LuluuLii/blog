## 分层结构
从顶向下是：
- 业务代码
- Nodejs 运行时
	- V8
		- JS 执行
		- GC：管理 js 堆内存：业务代码里创建的对象、数组、字符串、闭包等，大部分由 V8 管理，对象分配过快、生命周期过长、引用没有释放，都会影响 GC 行为，最终反映到请求延迟和进程内存上
	- libuv：Nodejs 适合高并发 I/O 场景，很大程度上因为它不需要为每个请求创建一个独立线程，而是通过事件循环和操作系统的 I/O 多路复用能力处理大量连接
		- 事件循环：几个阶段
		- 异步I/O 
		- 线程池
	- 注意点：
		- 要对是否占据 CPU 敏感，看是否 CPU 友好。Nodejs 主线程非常关键，JS执行、事件循环推进、回调调度都依赖主线程，如果主线程被同步 CPU 计算长时间占用，即使外部系统都很快，请求也会在 Node.js 进程内部排队（进程内的事件循环队列和内核的连接队列都会排队）
		- CPU 不友好的操作比如循环很多。
		- 异步 I/O 不会占用主线程，I/O 完成后的回调会占用主线程（异步等待过程交给底层机制处理，回调开始执行以后，JS代码在主线程上跑）-- 如果一次请求制造了大量连续微任务，事件循环也可能长时间没有机会回到 I/O 调度阶段
		- 特别注意同步代码的执行时间：一个接口里如果有大对象遍历、复杂 JSON 处理、大量正则匹配、同步加解密、同步压缩、同步文件操作，都会使事件循环无法及时处理其他请求
			- 大数组遍历：控制数据规模，必要时分片处理
			- 大 JSON 解析/序列化：限制payload大小
			- 复杂正则：可能出现灾难性回溯
			- 服务端请求链路中避免使用同步 fs API
			- 请求内密集计算：下沉到worker、独立服务或者异步服务，避免拖慢同进程其他请求
- 操作系统内核背景知识：**进程**是一个资源容器:独立的虚拟地址空间、文件描述符表、等等。进程之间内存是隔离的,想通信得走 IPC。**线程**是进程里的执行单元,同一进程的多个线程**共享**那份地址空间(堆、全局变量、fd),但各自有独立的栈、寄存器和程序计数器。关键的一点是:**CPU 调度的是线程,不是进程**。一个 CPU 核心在某一时刻只能跑一个线程。

## 适配场景
Node.js 的事件循环机制和主线程模型，决定了它适合进行 I/O 密集型操作。I/O 密集型场景：大部分时间花在等待网络、数据库、缓存或其他服务返回，而不是在本进程里做大量 CPU 计算的场景。比如 BFF，网关，接口聚合，页面服务端渲染，数据编排等。

libuv对操作系统能力的封装：
- 网络 I/O 上，libuv 会使用不同平台提供的高性能时间通知机制，例如 linux 上常见的 epoll，macOS s上是kqueue，Windows上是IOCP
- Nodejs 里不是所有异步能力都是由事件通知完成的，对于部分文件 I/O（除能在linux上走 linux io_uring 的 外，io_uring 是内核提供的真·异步 I/O 提交接口,libuv 可以把**一部分** fs 操作直接提交给内核异步完成）、DNS解析、压缩、加密等操作，libuv 会使用线程池进行，线程池可以避免这些操作直接阻塞主线程，但线程池本身是有限资源
	- 对于高频压缩、批量文件操作、大量加解密计算这类场景，要评估它们是否应该留在在线请求链路里。
	- UV_THREADPOOL_SIZE 可以调整线程池大小，但不是越大越好，过大的线程池会带来上下文切换和资源竞争，可能降低稳定性

对于CPU 密集型任务的处理：
- 拆分任务：例如循环/批处理可以分段执行，让事件循环有机会处理其他 I/O
- worker threads：计算逻辑仍希望留在 Node.js 应用内时使用，需要注意数据传输和序列化成本
- child process: 需要隔离执行外部命令或独立脚本，注意进程管理和超时控制
- 独立服务：计算能力通用切资源消耗较大，增加架构复杂度，但隔离性最好
- 异步离线任务：不要求请求内实时完成的，需要注意任务状态和失败重试机制

## 内存
### V8 内存与 GC
很多稳定性问题会落到内存和 GC 上，问题通常来自对象分配方式不合理、对象生命周期长、引用没有释放，导致 GC 成本越来越高。
可以把 V8 管理的堆内存简单分为新生代和老生代：
- Young Gen：刚创建、预期很快死亡的对象，比如 Web 服务请求中的临时数组、临时字符串、请求上下文对象等，如果这些对象很快不再被引用，就会在新生代 GC 中被回收。它很小(MB 级),内部又切成**两个等大的半区(semi-space)**,同一时刻只用其中一个,分配靠一个指针往前"顶"(bump-pointer),所以极快。回收用 **Scavenge(Minor GC)**,是一种复制式算法:GC 时把活着的对象从当前半区**复制**到另一个空半区,原半区整块作废、无需逐个释放,两个半区角色互换。
- Old Gen：存放时间更长的对象，例如全局缓存、长期连接对象、模块级对象、闭包持有的对象，以及经过多次 GC 后仍然存活的对象。大(GB 级），用 **Mark-Sweep-Compact(Major GC)**:标记可达 → 清除不可达 → 偶尔压缩整理碎片，现代 V8(Orinoco 那套)把大部分标记/清扫做成**并发+增量+并行**,尽量不长时间占住主线程。
对象晋升：
- 一个对象**熬过大约两次 Scavenge**还活着,就被判定"这大概是个长寿的",从新生代搬进老生代。唯一的例外是**尺寸**:超过阈值的大对象会被直接分配进专门的 Large Object Space,绕过新生代(它太大,复制成本太高,不适合走 semi-space 那套)
	- LO Space 是 V8 堆里和 Old Space 平级的一个独立 space
	- kMaxRegularHeapObjectSize：这个常量绑定在 **V8 的堆页(page)大小**上。当前 V8 的常规页是 256KB 量级,所以阈值就落在略小于一页、几百 KB 这个数量级。新生代/老生代的 GC 都可能要**移动(复制、压缩)**对象,而移动的前提是一个对象能**装进单个页**。超过这个尺寸的对象没法舒服地塞进常规页,于是被单独扔进 Large Object Space,给它自己的专属页,并且**从此永不移动**(GC 只标记/回收它,不搬它)。能进 LO Space 的是大**字符串、大数组(FixedArray)、大对象**这类 V8 堆内对象;而 `Buffer` / `ArrayBuffer` 的**数据实体是堆外(off-heap)分配**的,不走 V8 的 GC 堆,也就不占 LO Space
- 频繁创建大量对象，新生代 GC 频繁，分配压力过大，也会导致推高老生代占用。一个典型问题：请求里制造海量短命对象 → 疯狂触发 Scavenge、还把一批对象顶进老生代 → 老生代涨快 → Major GC 变频 → 尾延迟抖动
- ![[Screenshot 2026-07-03 at 01.06.28.png|546]]
- 可调旋钮
	- `--max-semi-space-size`(MB)调新生代半区大小——调大能减少 Scavenge 次数,对"疯狂 new 对象"的分配密集型负载有帮助,代价是多吃内存、单次 Scavenge 变长;
	- `--max-old-space-size`(MB)就是那个著名的、撞到 `JavaScript heap out of memory` 时要动的老生代上限。
		- GC 只能回收不可达(unreachable)的对象。撞到上限的那一刻,场景是:老生代已经逼近 `--max-old-space-size`,V8 触发了越来越激进的回收、直到最后一记的 full Mark-Compact,结果发现堆里的对象大多仍然可达(还被引用着),回收不动,用量压不回限制以下——于是抛出 `FATAL ERROR: Reached heap limit`,进程 abort
		- 信号：当活对象逼近上限,V8 会把越来越多时间耗在 GC 上想腾地方,表现为 CPU 被 GC 打满、吞吐骤降
		- 两种可能导致：
			- 内存泄漏：只增不删的全局 `Map`/数组/缓存、忘了 `removeListener` 的事件监听、捕获了大作用域的闭包、模块级持续累积、定时器/未清理的队列。特征是内存**单调爬升不回落**,给足内存也只是**推迟**崩溃
			- 一次性装了太多真·活数据: 不是泄漏(用完会释放),但**峰值工作集**超了限 ——比如把一个巨型文件/结果集**整个读进内存**、缓冲整个大上传/大响应、一次性构造巨大的中间结构。
			- 抓个 **heap snapshot**(`--inspect` / `--heapsnapshot-near-heap-limit`)看保留大小(retained size)是不是某个结构在无界增长:是,就去堵泄漏;不是、只是工作集大,就把它**流式化 / 分页 / 分片**处理。
需要注意/避免的开发行为：
- 请求内构造超大对象 --> 控制数据规模，采用分页、流式或分批处理
- 全局 Map 无上限缓存 --> 设置容量、TTL和淘汰策略
- 闭包捕获请求上下文 --> 只保留必要字段，不持有 req/res
- 事件监听器动态注册 --> 明确注销实际，避免请求级重复注册
- 大 buffer 一次性分配 --> 优先流式处理，避免一次性读入

### 堆内存、堆外内存和 RSS
我们写的业务代码是 JS，但 Node.js 本身、V8、libuv、OpenSSL、zlib、部分 npm 原生模块，很多都是 C/C++ 实现的。这些属于 Native 层。比如 fs.readFile 读大文件，底层文件读下、缓冲区和线程池由 Node.js / libuv 管理。

RSS（Resident Set Size）：操作系统视角下,你这个进程此刻真实占用的物理内存总量
- process.memoryUsage()
- 包含
	- V8 堆(`heapTotal`,也就是前面聊的新生代+老生代)
	- 堆外(external):`Buffer`/`ArrayBuffer` 的数据实体、C++ 对象等不受 V8 GC 管的部分 
	- 以及**代码段、线程栈、V8/Node 运行时自身开销**等
- 底层 allocator 可能会把释放后的内存先留在进程里复用，例如：GC 释放了对象,RSS 往往不会立刻降。V8 和底层分配器常把空出来的页留着复用、不急着还给 OS,所以你会看到 `heapUsed` 掉下去了、`rss` 却还挂在高位。
- 排查内存问题时，比较实用的方式是同时看 `heapUsed`、`external` 、`arrayBuffers` 和 `rss` 的趋势，以及 `rss - heapTotal` 或 `rss - heapUsed` 的差值变化，这样可以初步区分问题更偏 JS 堆对象泄漏，还是偏 Buffer/natvie/ 堆外内存增长。
	- 对于 JS 对象泄漏，重点沿着 Retainer 链路找是谁在引用
	- 对于堆外或 RSS 异常增长，重点排查 Buffer、流、native addon、压缩加密库、文件和网络缓冲等资源的生命周期

### 内存泄漏
一般表现：进程刚启动时正常，运行一段时间后内存逐步上升，GC 越来越频繁，请求延迟开始都懂，最后才出现 OOM 或进程重启。
常引起内存泄漏的模式：
- 全局缓存无限增长，key 数量持续增加 -> 必须有容量、TTL 或淘汰策略（使用 redis）
- 闭包持有大对象，请求结束后对象无法释放 -> 避免闭包捕获完整上下文
- 事件监听器累积 -> 注册和注销成对出现
- 定时器未清理 -> 生命周期结束时 clear
- 未消费或未关闭的流，连接、句柄、缓冲区残留 -> 明确处理 error、close 和销毁逻辑
- Buffer 或大文件处理不当，表现为 heap 不高但 RSS 上涨 -> 避免一次性读入，优先流式处理并正确关闭
- native addon 资源未释放 -> 确认模块是否有 destroy / close / dispose 类释放接口

## 多进程模型
单个 Node.js 进程里，JS 执行主要依赖一个主线程和一个事件循环，这个模型适合 I/O 密集型任务，但很难把多核 CPU 利用起来（第一节已经提到，一个 CPU 核心在**同一物理时刻只运行一个线程**，但可以交替运行属于同一个或不同进程的多个线程。）为了利用多核，Node.js 提供了 cluster 模块，可以启动多个 worker 进程。
每个 worker 都是一个独立的 Node.js 进程，有自己的 V8 实例、堆内存和事件循环。
在单进程 Node.js 中，libuv 的事件循环是 Reactor 模型的核心调度器，通过 epoll、kequeue 这类系统能力等待 I/O 事件，再把就绪事件转成 JS 回调执行。
到了 cluster 多进程场景，可以理解成多个 Reactor 再并行工作，Primary 进程负责创建 worker（每个 worker 是 `child_process.fork()` 出来的**独立进程**），并监听与分发连接给某个 workder（这里是简化说法，分发连接只在 round-robin 模式下由 Primary 做,shared-handle 模式下是内核做），每个 worker 内部都有自己的 libuv 事件循环，独立处理分到自己这里的连接、请求回调和业务逻辑。这样多个 worker 可以分布在多个 CPU 核上。
注意：
- worker 之间是**进程隔离、内存不共享**的,通信只能走 IPC。这和 `worker_threads`(同进程、共享内存)是两回事。因此：全局变量在不同 worker间不共享，不要把进程内 Map 当成全局一致性缓存
- 连接可能分布到不同 workder，因此请求级状态不能依赖进程内上下文，cluster 下没有共享状态，会话、锁、缓存一致性要依靠外部存储（例如 redis ）。一些例子如下：
	- **会话/登录态。** 用 `express-session` 默认的 MemoryStore,或自己写个 `const sessions = new Map()`。用户在 worker 1 登录、session 建在 worker 1 的内存;下个请求轮到 worker 3,它压根不认识这人——表现就是**莫名其妙随机掉登录**。外置到 Redis session store,或干脆用无状态的 JWT。
	- WebSocket/SSE 的跨连接推送。一条长连接只活在**某一个** worker 上。当你想给用户 X 推一条消息,而触发推送的那个 HTTP 请求/事件落在了**别的** worker——那个 worker 内存里的 `connections.get(userId)` 只看得到**自己这台**的连接,根本没有 X 的 socket。解法是加一层 pub/sub(Redis pub/sub 把消息广播给所有 worker,谁持有目标连接谁真正发出去),socket.io 的 Redis adapter 就是专门干这个的。
	- **去重/幂等/分布式锁。** 内存里存个"处理中"标记或"已处理的 requestId 集合"来防重复。重试或并发请求一旦打到**别的** worker,就绕过了你的标记 → **双重扣款、任务被跑两遍**。这种要用 Redis `SETNX`/Redlock,或者靠 DB 的唯一约束在存储层兜底。
	- **多步流程的中间态。** 向导式表单、分片上传:第一步/第一片把数据暂存内存,第二步/第二片落到别的 worker 就读不到了。中间态必须落到外部存储(或至少一个共享的临时区)。
	- **同源但不算 request 级**的经典坑:`setInterval`/cron 写在启动代码里,**每个 worker 都会各跑一份**,定时任务被执行 N 次而不是 1 次。这个得单独指定一个进程跑,或者上 leader election。
	- 判断准则:"如果同一个客户端的下一个请求换了个 worker,这份状态还能不能被找回?" 需要"跨请求存活 + 被再次找到"的,就不能放进程内存。

这也正是 cluster(以及任何多实例部署)的正道——**把 worker 做成无状态的,状态一律外置到 Redis/DB**

## 其他注意事项
- 缓存设计：所有缓存都要有上限、TTL 或淘汰策略
- 对象引用：不要长期持有 req、res、大上下文和大结果集
- Buffer/Stream：避免大文件一次性读入，流要处理 error、close 和销毁逻辑
- native 模块：使用图片处理、加解密、压缩等模块时，关注是否有底层资源释放要求
- 异常处理：未捕获一场要有日志和足够上下文，不能静默吞掉
- 应急
	- 止血 & 保留现场：优先动作是关流量，而不是删除或直接重建所有异常机器
		- 内存、GC、句柄、连接池、日志上下文这些信息在删除或重建后很难恢复
		- 如果关流量后仍持续影响，再考虑重建或回滚
